# Orchestrator Handoff Contract

## PURPOSE

Documents the package `jaxflow build`/`review --diff` generates and hands to the
one-shot model, and what the tech lead must author for that generation to work: the
plan named by `--plan` is the tech lead's actual deliverable. A one-shot cannot ask
questions, so the generated package must be complete by construction from a
well-formed plan.

The wrapper injects `run_id`, project slug, role, phase, and the report path. Do NOT
restate them. Do NOT restate role rules — the role contract carries them. The BUILDER
PACKAGE and REVIEWER PACKAGE below are generated, not authored: prose read by the
one-shot model, not parsed by the wrapper — the layouts are illustrative of what the
model actually receives.

## WHAT JAXFLOW DOES / WHAT THE TECH LEAD ENSURES

`jaxflow build` reserves its own worktree and creates the branch itself, against a base
SHA it resolves from `--base` — nothing is left for the tech lead to create or check out
by hand. `jaxflow build --resume <run_id>` reuses that recorded worktree and the prior
plan/phase/whitelist/verify/build/base; do not pass those fresh-build flags, and do not
recreate the worktree. `review --diff <build_run_id>` resolves both diff endpoints itself and locates
the builder's `.tests.txt` itself, from that build run's own manifest — nothing is left
for the tech lead to resolve or locate by hand either. The wrapper refuses reviewer
dispatch when the linked builder run's recorded `head_sha` differs from the diff's
resolved `<head-sha>`.

What the tech lead still ensures before dispatching:
- A clean control-repo tree.
- The base ref to pass as `--base` (`jaxflow build`) and the branch name to pass as
  `--branch`.
- A plan (for `build`) meeting the PLAN AUTHORING MUST list below — `jaxflow build`
  validates it before reserving a worktree and refuses a defective one.

## BUILDER PACKAGE

Generated by jaxflow from the plan named by `--plan` — not authored here. jaxflow does
not extract a goal, task list, or acceptance criteria from the plan text: the builder
reads the plan whole (see PLAN AUTHORING below) as its own goal/tasks/acceptance
source. `paths.spec` comes from the plan's OPTIONAL `**Spec:**` line, fragment included
when present — absent, jaxflow names the plan itself as the spec; `paths.plan` is
always the plan itself; `commands.test`/`commands.build` are whatever the tech lead
passed to `jaxflow build --verify`/`--build`.

```markdown
read-scope: <one absolute path per line — the validated READ-ONLY scope the builder may
  read named originals from: the control repo, the assigned worktree, and an explicitly
  validated external document parent. Reads only: every write stays in the assigned
  worktree>
paths:
  spec: <absolute path — the ORIGINAL document, read in place from the validated read
    scope: control repo, assigned worktree, or an explicitly validated external document
    parent — never a copy; may carry a `#<heading>` fragment>
  plan: <absolute path — the ORIGINAL document, read in place from the same scope>
  refs: <one absolute path per line to any docs, screenshots, fixtures the builder
    needs — each refs path MUST resolve inside the same validated read scope as
    spec/plan: the control repo, the assigned worktree, or an explicitly validated
    external document parent>
assumptions: <facts the builder may rely on without verifying: "endpoint X exists",
  "auth is already wired", "no new deps needed">
commands:
  test: <ONE shell command string — pipelines and `&&` chains are one command — or
    `none`>
  build: <ONE shell command string — pipelines and `&&` chains are one command — or
    `none`>
verification: rafa-verifies | agent-verify: <tool + check> |
  agent-deploy-verify: target=<preset's Verification deployment target>; check=<check>
  # overrides the project AGENTS.md verification default for THIS phase
  # agent-deploy-verify is invalid when the preset's Verification deployment target is none
out-of-scope: <what the builder must NOT touch, even if tempting — or `none`>
```

## PLAN AUTHORING

The plan named by `--plan` is the tech lead's actual deliverable. `jaxflow build`'s only
handoff input is that plan — there is no separate flag for pasting a prose package by
hand.

MUST carry — exactly what `jaxflow build`'s pre-dispatch validator checks, no more:
- An OPTIONAL `**Spec:**` line, optionally with a `#<heading>` fragment (the fragment
  names a heading to read from, through the next heading of the same or higher level,
  instead of the whole document — see `builder-contract.md`/`reviewer-contract.md`).
  When present, the line — fragment included — MUST resolve: the path is canonical,
  non-secret, readable, inside the allowlist, and any fragment names a real heading in
  the resolved document. When absent, jaxflow names the plan itself as the spec, exactly
  as `review --diff` already does when no build-time spec was recorded.

There is no required heading structure — jaxflow no longer parses a `**Goal:**`/H1 line
or `### Task N:` headings out of the plan; the whole plan text is what the builder
reads. A plan carrying a `**Spec:**` line that does not resolve is refused before
`jaxflow build` reserves a worktree — no worktree, no branch, no run.

SHOULD carry — authoring guidance the tech lead is responsible for but jaxflow does not
check:
- A goal statement and a per-task breakdown, with objective acceptance criteria stated
  under each task — jaxflow's generated package no longer carries a `goal`/`tasks`/
  `acceptance` summary of its own, so the plan text itself is the builder's only source
  for them.
- The target files/functions and exact changes per task.
- Applicable constraints.
- The test/build commands the tech lead passes to `jaxflow build --verify`/`--build`.

## COMMANDS

Prefer a quiet reporter for `commands.test`/`commands.build` (`vitest run
--reporter=dot`, `pytest -q`, `tsc --pretty false`) — the wrapper's own evidence capture
already keeps only the last 50 lines per command regardless of verbosity, so a verbose
reporter only inflates the command's own run time and the builder's context, never the
persisted evidence file.

The wrapper runs each `commands.*` string via `/bin/sh -c`: any pipeline in a command
string MUST preserve the producer's exit status. Do not pipe a test/build command's
output through anything that discards or overwrites its exit code (e.g. a trailing
summarizer) — the wrapper reads the pipeline's own exit status, not the underlying
tool's, and a masked non-zero exit is reported as a pass.

## REVIEWER PACKAGE

Generated by jaxflow's `review --diff` dispatch stub from the build run it targets —
not authored here.

```markdown
Correction review of <prior_review_run_id> (verdict <prior_verdict>)
  # optional leading line -- present only on a correction round (`review --diff --since`)
diff: <full-base-sha>..<full-head-sha>
  # both full 40-character resolved commit IDs -- jaxflow resolves them itself, e.g.
  # 3f9d2c1e8b7a6d5c4b3a2f1e0d9c8b7a6f5e4d3c..9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b
  # never a ref, tag/tree object, or abbreviated prefix
paths:
  spec: <absolute path — may carry a `#<heading>` fragment>
  plan: <absolute path>
  test-output: <absolute path to the literal, existing
    <repo>/.local/reports/<builder-run-id>.tests.txt of the builder run that produced
    <head-sha> (redacted evidence)>
  prior-review: <absolute path to the prior review's report — present only on a
    correction round (`review --diff --since`); see reviewer-contract.md>
```

Never include the builder report, its summary, or its conclusions — the reviewer's
envelope is sealed by design (see `reviewer-contract.md`). `paths.prior-review` is the
one exception, on a correction round: the prior REVIEW report, additive to the sealed
envelope, never the sealed builder report.

## LEAD RUNTIME ADDENDUM

Applies only when the tech lead runs on a runtime that cannot signal "waiting for input"
(currently: Codex — its notify hook fires only on turn completion). Under such a lead:

- Every final assistant message MUST be a complete, self-contained proposal AND MUST
  BEGIN with a decision capsule of at most 300 characters containing the
  recommendation, its material scope, and the explicit ask ("approve / choose /
  reject"). The hook forwards that leading 300 chars verbatim — everything after it is
  context the owner may never see.
- Never end a turn with a bare question, a menu without a recommendation, or a wait
  state.
